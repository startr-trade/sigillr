# v0.1.0

_Released 2026-11-22._

The first release of Sigillr claims the name on crates.io and sets up the project: the `sigillr` command, its build and release pipelines, the user guide, the brand, and the licence and community files. Sigillr does not run as a service yet. Registration, lookup and the OpenID Connect provider arrive in the next releases.

## What you can do

- Install it with `cargo install sigillr`, with a binary from the GitHub release (Linux x86_64, macOS x86_64 and arm64, Windows x86_64), or with `install.sh` / `install.ps1`, which refuse an archive whose SHA-256 does not match.
- Run `sigillr --version` and `sigillr --help`. The help lists the commands later releases add: `serve`, `lookup` and `index rebuild`.
- Read the user guide: what Sigillr is, running an instance, and the configuration reference, with every setting marked as planned.

## For contributors

- A Rust workspace on a pinned toolchain (1.99.0), with one crate per component (`sigillr-web`, `sigillr-api`, `sigillr-store`, `sigillr-index`). The component crates hold no code yet and are not published.
- `make ci` runs what GitHub Actions runs, cheapest check first: format, clippy with warnings as errors, cargo-deny (advisories, licences, sources), clippy for Windows and macOS, and the tests on Linux, macOS and Windows. Dependency changes also run a no-C-compiler build proof. CodeQL runs once per release.
- Repository checks (`sigillr-archtest`) hold the toolchain pin, SHA-pinned actions, licences, brand assets, README, guide links and release workflow in place. They also keep product text free of any one agent vendor's name: write "your agent", and name a framework only in its adapter's files.
- Releases ship only from a commit whose CI passed. Each release carries checksums, a CycloneDX SBOM and a build-provenance attestation, and is scanned for known vulnerabilities before it is published.
- Licensed MIT OR Apache-2.0. Report vulnerabilities privately through GitHub (see SECURITY.md).
